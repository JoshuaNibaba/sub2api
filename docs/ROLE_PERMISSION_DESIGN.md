# 角色与权限设计

## 目标

当前版本把用户分成四种内置角色：

| 角色值 | 中文名称 | 定位 |
|---|---|---|
| `super_admin` | 超级管理员 | 继承历史 `admin` 的全部能力 |
| `admin` | 管理员 | 受限的后台管理能力 |
| `user` | 用户 | 现有普通用户能力 |
| `enterprise_user` | 大客户 | 用户能力 + 脱敏号池/用量/日志能力 |

数据库迁移 `239_expand_user_roles.sql` 会把已有 `admin` 记录迁移为 `super_admin`，保证升级后已有管理员不丢权限。新建的受限管理员使用 `admin`。

## 核心原则

角色不是授权判断的最终依据，权限才是。后端使用 `internal/domain/permissions.go` 中的权限标识和默认角色矩阵；路由中间件、业务服务和前端路由都应该依赖权限标识，不要新增散落的 `role == "admin"` 判断。

当前权限矩阵是代码内置的默认策略：

- `super_admin` 自动拥有所有已声明权限。
- `admin` 拥有面板、用户、分组、用量、运维读取和部分管理权限，但不拥有系统、凭据、支付配置、插件、审计等高风险权限。
- `user` 不拥有后台权限。
- `enterprise_user` 只拥有企业只读能力。

权限标识采用稳定的点号命名，例如：

```text
admin.users.read
admin.users.write
admin.users.role_manage
admin.credentials.read
admin.system.write
admin.ops.write
admin.usage.write
admin.audit.write
enterprise.account_pool.read
enterprise.usage.read
enterprise.logs.read
```

## 修改权限是否需要大改

不需要。默认矩阵集中在一个文件中。给角色增删已有权限时，只需修改：

```text
backend/internal/domain/permissions.go
```

然后运行后端测试即可。路由和页面只依赖权限标识，不需要修改数据库结构，也不需要批量修改用户数据。

新增一个权限时，通常只需要：

1. 在后端声明新的 `Permission` 常量。
2. 在默认角色矩阵中给需要的角色加入或移除它。
3. 在目标路由上增加 `RequirePermission` 或 `RequireReadWritePermission`。
4. 若前端需要隐藏菜单或按钮，在 `frontend/src/utils/permissions.ts` 增加同名常量和界面判断。
5. 添加权限矩阵测试和接口 401/403 测试。

这意味着“某个角色增加/删除一个已有权限”是小改动；“新增一个业务模块”才需要新增接口、DTO、界面和测试。

## 读写权限

对于同时包含查询和变更的路由组，使用：

```go
middleware.RequireReadWritePermission(
    service.PermissionAdminUsersRead,
    service.PermissionAdminUsersWrite,
)
```

GET/HEAD 请求检查 read 权限，POST/PUT/PATCH/DELETE 检查 write 权限。这样受限管理员可以读取允许范围的数据，但不能因为获得列表权限而获得写权限。

## 账号归属中间件

权限只回答“这个角色能不能碰账号接口”，不回答“能不能碰这一个账号”。后者由三个按行判定的中间件负责，超级管理员一律放行：

| 中间件 | 用在哪里 | 判定方式 |
|---|---|---|
| `RequireAccountRouteAccess` | `/admin/accounts` 整组 | 允许创建账号；其余写操作必须命中 `/admin/accounts/:id...` 且账号归属当前用户 |
| `RequireOwnedAccountParam` | 账号组之外、以 `:id` 直接寻址账号的路由（上游额度、余额、套餐、定时测试等） | `:id` 即账号 ID，校验归属；组内不带 `:id` 的路由交回该组自身的权限中间件 |
| `RequireOwnedAccountVia` | 以子资源 ID 寻址的路由（例如定时测试计划 ID） | 先把路由 ID 解析成所属账号 ID，再套用同一条归属规则 |

后两个是必需的，因为那些路由组只要求 `admin.accounts.read`：没有它们，受限管理员可以读取他人账号的上游额度和余额，甚至用对方的凭据触发真实的上游探测。

## 角色管理保护

创建或修改管理员角色需要 `admin.users.role_manage`，默认只授予超级管理员，并继续要求 step-up 二次验证。后端不信任前端下拉框；即使直接调用 API，也会拒绝受限管理员的角色提升、降级或超级管理员创建操作。

## 大客户数据边界

大客户看到的是真实号池，不是另做一套“演示页”。界面上复用原有的账号管理页面和用量记录页面，数据来自独立的 `/api/v1/enterprise/*` 只读接口，绝不复用 `/api/v1/admin/*`：前端在企业角色下把同一个页面指向企业接口，后端则用单独的脱敏 DTO 应答，因此给管理员 DTO 新增字段不会意外泄露给大客户。

脱敏投影 `dto.AccountFromServiceMasked` 明确列出保留字段，而不是从管理员 DTO 里删字段：

- 保留运营状态：平台、类型、状态、是否可调度、并发上限与当前并发、负载系数、优先级、分组、最近使用时间、到期时间、限流与会话窗口计时器。
- 账号名称部分脱敏：长度 ≤ 4 个字符时整体替换为 `****`，否则保留首尾各两个字符（`sh****ai`）。
- 移除身份、凭据与计价信息：归属人、备注、**代理服务器**、OAuth token / API Key / Cookie / 完整凭据 JSON、厂商扩展配置、原始错误文本、倍率与上游计费倍率。
- 移除仅管理员可用的调度内部量：调度评分、窗口成本、活跃会话数、RPM。保留当前并发，因为“这个号忙不忙”正是号池视图存在的意义。
- 名称搜索只对员工角色开放。名称既然是脱敏的，允许大客户按名称搜索等于提供一个存在性判定接口，可以逐字符还原真名。
- 号池不隐含 `status=active` 过滤：空过滤条件返回管理员页面同样会列出的全部账号（含限流、异常）。状态在该投影里本就是公开字段，隐藏只会让客户看到的容量与运维看到的不一致。
- 日志默认只允许本用户、授权分组或授权业务范围，并清理 Prompt、请求头、Token 和上游响应体。

## 企业只读接口

后端保留三类企业范围接口作为权限隔离的数据源，前端不新增独立企业页面，而是复用原有的账号管理和用量记录页面：

- `GET /enterprise/account-pool`：由原有账号管理页面在企业角色下调用，使用与管理员页面相同的分页信封（`AccountListItemWithConcurrency`），逐行返回脱敏号池。
- `GET /enterprise/usage-logs`：由原有用户用量页面调用，仅返回当前登录用户自己的用量记录，并带上脱敏命中账号。
- `GET /enterprise/error-logs`：由原有用户用量页面调用，仅返回当前登录用户自己的脱敏错误记录。

这些接口的后端权限分别是 `enterprise.account_pool.read`、`enterprise.usage.read` 和
`enterprise.logs.read`。前端菜单和路由只负责体验，后端权限检查和数据范围检查始终有效。

### 复用页面时的只读约束

账号页面在企业角色下进入只读模式，原则是“不显示做不了的东西”，避免出现永远空白的列或点了必然 403 的按钮：

- 隐藏批量选择列、行操作列和所有写操作入口；不加载任何 `/admin/*` 接口。
- 隐藏脱敏掉的列：代理、备注、倍率、上游计费倍率；以及依赖员工接口的调度评分和今日统计列。
- 关闭名称搜索框和隐私模式过滤器——后端不接受前者，也不处理后者，留着只会是无效控件。
- 分组名称来自大客户自己有权访问的 `/groups/available`，因此分组列和分组过滤器显示真实名称，而不是裸的分组 ID。
- 自动刷新定时器不启用：其开关属于员工工具条，客户无法关掉。

## 账号归属与请求命中可见性

账号表通过 `owner_user_id` 记录归属：新建账号默认归属于创建它的登录用户，超级管理员可以在创建或编辑时指定归属。历史账号没有归属时视为共享账号。

- 超级管理员可以完整查看和管理所有账号。
- 受限管理员可以完整查看并**完整运维**自己拥有的账号：除了改名和删除，还包括连通性测试、清除错误、清除限流、恢复状态、重置配额、切换可调度、同步上游模型、临时不可调度和上游计费探测等所有 `/admin/accounts/:id/...` 行内操作。“拥有一个账号”必须意味着能把它跑起来，只能改名却不能清限流的角色无法完成它存在的职责。
- 受限管理员仍被挡在三类按账号寻址的接口之外：`/:id/duplicate`、`/:id/apply-oauth-credentials`、`/:id/shadow`。它们要么写入新的凭据材料，要么从源账号的凭据派生出第二个账号，而从凭据创建账号需要 `admin.credentials.read`，该角色没有这个权限。（另外 `DuplicateAccount` 目前不会把 `owner_user_id` 带给副本，副本会变成共享账号。）
- 不针对单个账号的接口（批量更新、批量凭据写入、CRS 同步、数据导入导出）对受限管理员一律拒绝。
- 前端对应收敛：行内“更多”菜单对自己拥有的账号恢复可用，但其中依赖凭据的四项（复制账号、重新授权、刷新 token、创建 Spark 影子号）由 `credentialActions` 开关关闭，否则点了只会拿到 403。
- 对共享或他人账号只能看到基础信息，账号名称使用 `****` 部分脱敏，不返回代理详情、凭据、扩展配置或原始错误信息。
- 大客户同样只能看到脱敏号池；不会因为拥有企业权限而获得代理服务器或凭据。即使超级管理员把某个账号归属给了该大客户，他看到的仍然是脱敏行——归属只影响员工角色的可见范围。
- 受限管理员和大客户的请求日志都强制限制到当前登录用户，并返回本次请求命中的账号名称；非本人账号仍使用 `****` 脱敏，避免无法核对路由或被注水。

数据库迁移 `240_add_account_owner.sql` 为历史账号保留 `NULL` 归属，升级后由超级管理员重新分配即可。

## 将来做成后台可配置

当前矩阵是代码内置的，优点是简单、可审查、部署后行为确定。以后如果需要在管理面板中动态调整角色权限，可以在不改变调用方的前提下增加：

1. `role_permissions` 表（role、permission、enabled、updated_at）。
2. 权限仓储和 Redis/进程缓存。
3. `PermissionResolver`：先读数据库覆盖，再回退到代码默认矩阵。
4. 超级管理员专用的角色权限编辑页和审计日志。

路由和服务层仍然调用同一个 `HasPermission`/`RequirePermission` 接口，因此不需要重写业务模块。这个演进路径可以把“改代码发布”升级为“超级管理员在面板中调整权限”，同时保留代码默认值作为灾备回退。

## 安全要求

- 前端权限只用于菜单、页面和按钮显示，不能代替后端授权。
- 权限变更、角色变更、敏感数据读取和高风险写操作必须进入审计日志。
- 新权限默认不开放给任何低权限角色，先写测试再加入角色矩阵。
- 任何涉及凭据、备份、系统更新、插件、支付密钥和原始审计日志的权限都应默认只给超级管理员。
